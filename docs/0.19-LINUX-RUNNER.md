# Linux runner amendment for the 0.19 campaign

Prepared November 6, 2026. This changes host instrumentation and execution location,
not E1–E3 datasets, queries, seeds, run order, feature parity or acceptance thresholds.
The engine protocol and [campaign](0.19-CAMPAIGN.md) remain authoritative.
Full timings require qualified Linux artifacts, a new frozen manifest and independent
review. A successful smoke test does not authorize performance claims.

## Environment and artifacts

Use an isolated working directory on persistent storage, such as
`~/mnestic-benchmarks-work`, with sibling `mnestic` and `mnestic-benchmarks` checkouts.
Store environments, artifacts, logs and fresh campaign roots alongside them.
Do not use `/tmp` if it is tmpfs: RAM-backed database storage changes both memory
pressure and the interpretation of backend timings. The guard rejects tmpfs/ramfs.
It resolves symlinks and checks free space on the campaign volume, rather than `/`.

The proposed development VM exposes four x86-64 logical CPUs, approximately 16 GiB
RAM and an ext4 root volume. Its initial sample had 7.2 GiB free disk and 9.6 GiB
available RAM, no swap and no reported CPU steal. These are preparation observations,
not evidence of a quiet full run or dedicated physical CPUs. Other development
services remain running; do not stop shared services as part of launcher setup.

Use Linux x86-64 release wheels for released 0.18.0 and the immutable 0.19 candidate.
Record wheel hashes, installed extension hashes, source SHA, build workflow and
compiler/features, Python version and complete dependency freezes. Use the same
Python and harness dependencies in separate baseline/candidate environments.
The hosted 0.19 wheel is built by workflow 42218579557 at
`0035030eac5b27d6f26b23a83675ec682d358cb3`; it still needs qualification on this host.
This remains a released-package comparison, not an isolated source-only A/B.

## Operational gates

The guard retains the 60-second quiet preflight, CPU idle >=85%, >=3 GiB free disk,
no native builds, swap-in <=16 MiB per ten-second sample and no swap-out.
The portability amendment adds >=2 GiB available RAM and <=1% CPU steal per sample.
Linux servers without a battery record power checking as not applicable; Linux
machines with batteries and macOS machines still require external power.

During execution the guard checks every ten seconds. A build or loss of external
power, or free disk below 1 GiB, interrupts immediately. Three consecutive samples
with any monitored process >=25% of one CPU, CPU steal >1%, available memory below
1 GiB, swap-in >16 MiB, or any swap-out interrupt the campaign. Linux monitors all
visible processes except the guard and its campaign process group; macOS retains
its existing background-service list. This is a sampled operational safeguard,
not proof that host-level interference is absent. No automatic retry is allowed.

The host record includes CPU description, RAM, power-check applicability and storage
mount. Linux `ru_maxrss` is converted from KiB to bytes; macOS values are already bytes.
Include `hybrid_recall/host.py` in the frozen harness hash list.

## Execution and recovery

First run the focused harness tests and tiny workload against both builds and both
backends. Preserve smoke logs separately from full timing rows. Then freeze absolute
VM paths in a new manifest with `qualification_ready: true` only after all package
and review gates pass. Old Mac manifests and rejected candidates cannot be reused.

Launch the frozen guard from the benchmark checkout within a persistent `tmux`
session. Confirm the session survives detachment and the VM is not scheduled to stop.
SSH disconnection does not stop a detached tmux session; VM shutdown still does.
No public listening port is needed. Keep status/guard/supervisor logs and raw JSONL
on the VM and copy them back for analysis.

The existing supervisor runs the twelve build/backend/seed combinations sequentially
and removes each explicitly generated database after its process ends, retaining
raw observations and status. The 7,200-second per-run cap remains unchanged; no
completion-time promise is inferred from the VM specifications. A new root is
required after interruption. Results describe this Linux VM and must not be pooled
with historical macOS timings.
