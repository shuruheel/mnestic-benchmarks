E1 uses the unchanged small workload (40k chunks, 10k entities, 50k edges,
384 dimensions, 1,000 queries, k=10, pool=100, hops=2, RRF=60), with 100 warmups
per path and all 1,000 measured queries. Decomposed retrieval makes four calls
(vector, FTS, entity traversal, mention lookup); native makes one call with three
signals. Its directed `link` projection stores both entity directions and outbound
entity-to-chunk links, so max_hops=3. The native leg's candidate/tie behavior is
engine-defined; report its own recall rather than imply equivalence to the
three lists truncated to 100 in the exact oracle. No concurrent QPS is measured.

Freshness records every attempted write as a separate mutation observation,
including elapsed time and the raw error. `hnsw::repair_limit` rejections are
counted explicitly. The first write error stops that run without retry or a
visibility probe; it cannot qualify the workload. Rejection counts from a stopped
run are censored observations, not an estimated production rejection rate.

Freshness uses all 200 writes in one atomic script per write. Each write appends
a unique FTS token and probes exact primary-key, FTS, exact mention-index, ANN,
decomposed and native paths, immediately and in that order. `ack_to_probe_ms`
includes earlier probes; `ms` is the individual probe time. There is no sleep,
retry or eventual polling. These sequential first probes do not measure each
signal at precisely the same instant. Rollback checks exact rows, FTS and ANN.

E2 fixes 20 queries per small build (the first 20 of the E1 bank), with both
random and adversarial eligibility for 100%, 10%, 1%, 0.1%, empty and three-key
sets. Adversarial sets occupy the far end of exact vector order. It records all
eligible keys and hashes. Compare post-filtered global prefix=100, filter ef
100/200/400/800/1600, and an exact eligible-key join. `is_in(cid,$eligible)` is the
HNSW predicate: its list-membership cost is included and may be substantial.

quality/cost sweeps, not the 250-ms widening gate. Native visit counts are unavailable.

FTS uses `candidates:$eligible` and corpus-global BM25 (engine defaults k1=1.2, b=.75). The E2 oracle breaks score ties by key; the historical E1 oracle retains k1=1.5 and generation-position component ties, so E1 recall includes that documented scoring/tie difference. It retrieves up to the
eligible count before ordering by score then key and limiting to 10, so engine
heap tie truncation does not silently select a different equal-score subset.
This deterministic reference costs more than an unspecified engine top-k tie.
Vector+FTS fusion uses these two lists only, pool=10, RRF=60, key ascending ties.

algorithm is selected by these results.
